# Experiments

`src/experiments.py` runs every experiment of `src/experiments.yaml` on every split seed (42, 0, 1) of CropOrWeed2 (`data/seed<N>/`), sequentially (experiment → seed). An experiment names a `setup`, `train` overrides of the setup's config and `eval` args, passed to the framework's own CLI/API. Per cell it trains with `yolo segment train cfg=src/yolo/configs/seg.yaml ...` or upstream's `python -m src.eomt.cli fit -c src/eomt/configs/seg.yaml ...` (a subprocess), then evaluates on test at native resolution at the experiment's `eval` batch (the largest that fits a GPU; the speed is per-image time at that batch, single-image latency is measured separately) with `YOLO(best.pt).val()` or upstream's `validate` (docs/evaluation.md). Checkpoints are `weights/{best,last}.pt` (YOLO) / `weights/{best,last}.ckpt` (EoMT, from the runner's `ModelCheckpoint`). Trailing `key=value` args are passed to the training CLI (Ultralytics args or dotted LightningCLI keys). Current experiments:
- Downsampling regimes, 1024x592 and 1280x736: the whole 1920x1088 frame downscaled to 1024 or 1280 wide (1024x580 / 1280x725, rounded up to multiples of EoMT's 16 px patch). They replace the square `ft-640`/`ft-1280`/`eomt-640`/`eomt-1280` boxes (2026-10-07).
  - `yolo-1024x592` / `yolo-1280x736`: vanilla Ultralytics fine-tuning for a fixed 50 epochs (same budget for every experiment; with yolo26m-seg, 100 epochs took ~2.6 h per 1280 cell for ~+0.01 mask mAP50-95 per 10 late epochs) at `imgsz` 1024 (batch 48) / 1280 (batch 32). Ultralytics trains only at a square integer `imgsz` (`rect=True` disables mosaic and shuffling), so training keeps mosaic on a square canvas with the frame downscaled exactly as in the rectangle; `val()` batches rectangles itself (stride 32, padded): 1024x608 / 1280x768. (A COCO zero-shot baseline was dropped as useless for comparisons.) Training is data-loading bound (decoding/mosaicking 1920x1088 JPEGs), so both use Ultralytics' `cache: ram` (images decoded once, stored resized to `imgsz`: ~14 GB at 1280, ~9 GB at 1024, per GPU process under DDP) and `workers: 4` per GPU process: at 1280 with 12 workers, DDP peaked at ~33–37 GB RSS per GPU process and exhausted the machine's 112 GB RAM; with 4, a full-data epoch left ≥ 15.5 GB available (~1:10 per epoch). A DDP smoke run at 1024, batch 48 peaked at 42 GB GPU memory per GPU. This machine runs **earlyoom** (SIGTERM to the largest process below 10% free RAM), so an out-of-RAM run dies with a torchrun `ChildFailedError` "Signal 15 (SIGTERM)" and no Python traceback; `journalctl -t earlyoom` shows it. `--device both` trains each run with DDP on both GPUs (the fixed batch is split across them); evaluation runs on the first GPU.
  - `eomt-1024x592` / `eomt-1280x736`: EoMT-S (`eomt-seg`), the same 50-epoch budget, `img_size` [592, 1024] / [736, 1280] ([h, w]): the whole frame scale-jittered into it in training (`seg.yaml`'s `scale_range` [0.5, 1.5], relative to the frame fit into `img_size`), resized to fit + padded in evaluation. `batch_size: 8` per GPU (16 total with `--device both`, as upstream); train/eval overrides are dotted LightningCLI keys, `eval` sets the training `img_size`.
- `eomt-native-1024` (EoMT only: Ultralytics loads and crops at the same `imgsz`): trained on random 1024x1024 crops of the frame at native resolution, without scale jitter (`scale_range: null`), dropping instances with less than 25% of their mask inside the crop (`min_visible_fraction: 0.25`; a crop left with no instance is redrawn, upstream's rule). The in-training validation (best-checkpoint selection) scores a fixed 2x2 grid of 1024 tiles per frame (`val_tile_size: 1024`, `TiledDataset` in docs/eomt.md), each as its own image, with instances < 25% inside the tile as `is_crowd`. The test evaluation stays on full frames (the CropAndWeed protocol, comparable with YOLO): native 1024 tiles merged back (`eval_tile_overlap: 640`, the module edit in docs/eomt.md), 4x2 per frame, overlapping by ≥ 640 px (725 px = 71% across, 960 px down since 1088 > 1024). The 640 px come from the largest objects (seed 42, non-crowd, all splits): the very largest spans the whole frame (1919 px wide), which no tile holds, so it is set by the 99th percentile of the longest box side, 638 px; 99.6% of instances lie whole in some tile (3 columns, 576 px overlap: 99.1%).
- All EoMT cells set `trainer.check_val_every_n_epoch: 5` (decided 2026-10-03; upstream/`seg.yaml`: 2): validation (best-checkpoint selection) at epochs 5, 10, …, 50. Lightning then saves `last.ckpt` only with each validation, so a crash loses up to 5 epochs.
- The native-resolution crop experiments (`crop-640`/`crop-1024`, YOLO; `eomt-crop-*`, EoMT) were dropped on 2026-10-06: they needed our own trainer subclasses.
Training seed stays at the config's 42; only the split varies across seeds.

**Measured epoch times** (2026-10-07; seed 42, DDP on both RTX PRO 6000s, one training epoch per cell with a full validation pass; `limit_val_batches=1` given on the command line was not honoured, so the val passes are measured, not extrapolated):

| cell | train epoch | val pass (+ metric compute, plot) | per epoch, amortised | 50 epochs |
|---|---|---|---|---|
| `yolo-1024x592` | 1:12 (113 steps) | 0:13, every epoch | 1:26 | ~1.2 h |
| `yolo-1280x736` | 1:40 (169 steps) | 0:21, every epoch | 2:02 | ~1.7 h |
| `eomt-1024x592` | 3:17 (337 steps) | 10:04 + 1:16 (70 batches), every 5 | 5:33 | ~4.6 h |
| `eomt-1280x736` | 3:43 | 8:56 + 1:01 (70 batches), every 5 | 5:42 | ~4.8 h |
| `eomt-native-1024` | 3:37 | 17:16 + 4:18 (277 batches, 4420 tiles), every 5 | 7:56 | ~6.6 h |

YOLO's first epoch also caches the images in RAM (~25 s: 9 GB at 1024, 14 GB at 1280 per process). EoMT's validation is 40–55% of its run time, almost all of it torchmetrics' mask mAP update encoding 100 full-resolution masks per image on the CPU (~8.6 s per batch of 2 x 8 frames), not the model. Per seed the five cells train in ~19 h, ~57 h for all three seeds, plus each cell's test evaluation.

**After the val speed-ups** (GPU resize, `val_batch_size`, and the GPU mask mAP `src/eomt/mask_ap.py` replacing torchmetrics; 2026-10-07), from single-GPU passes over ~3 batches (2 GPUs split the frames): an EoMT val pass is ~1.2 min on `eomt-1024x592` (0.13 s/frame; was 10:04), ~1.5 min est. on `eomt-1280x736` (was 8:56), ~2 min for `eomt-native-1024`'s 4420 tiles (0.054 s/tile; was 17:16); `compute()` < 1 s. Training epochs are unchanged.

| cell | per epoch, amortised | 50 epochs | test eval (one GPU) |
|---|---|---|---|
| `yolo-1024x592` | 1:26 | ~1.2 h | ~2 min (batch 64) |
| `yolo-1280x736` | 2:02 | ~1.7 h | ~2 min (batch 64) |
| `eomt-1024x592` | ~3:32 | ~2.9 h | ~4 min (batch 16, 0.19 s/frame) |
| `eomt-1280x736` | ~4:01 | ~3.4 h | ~5 min (batch 16, est.) |
| `eomt-native-1024` | ~4:01 | ~3.4 h | ~11 min (batch 4 frames, 0.55 s/frame) |

The EoMT test eval's framework metric is `MaskAP` on native masks (it reproduces hotcoco's CropAndWeed score); hotcoco scores the native `predictions.json` in seconds (11 s for YOLO's 315k test masks). About 13 h per seed including the test evaluations, ~39 h for the three seeds.

Per cell `<exp>/seed<N>`: training under `output/experiments/<cell>/train/` (`.done` once finished), val scratch under `.../eval/`, and `results/experiments/<cell>/{cropandweed.csv, summary.json}`. `summary.json` holds the CropAndWeed-protocol mask stats (mAP50-95, mAP50, mAP50-95 small/medium/large), per-class mask AP, the framework's own mask metrics and latency. After every cell, `results/experiments/summary.csv` (one row per cell: those stats without per-class AP, the framework's mAP50-95(M), latency) and `summary_agg.csv` (mean/std over seeds) are rebuilt. Cells with a `summary.json` are skipped (`--force` re-evaluates, reusing finished training); unfinished training resumes from its last checkpoint; a failed cell is logged and the loop continues. So relaunching the same command continues a crashed run. Each cell runs in its own child process (the same CLI with the hidden `--in-process` flag) whose output is appended to `output/experiments/<cell>/run.log`; afterwards the runner SIGKILLs every process tagged with that cell's `EXPERIMENTS_CELL_TOKEN` environment variable (inherited by torchrun, the ranks and their data-loader workers), since a crashed DDP run otherwise leaves data-loader workers alive holding their RAM caches (which made the next cells run out of RAM too). A process group wouldn't do: torchrun starts each rank in its own session, and a killed rank's workers are reparented. A failed cell's report also lists the DDP ranks' own exception lines (`[rankN]: ...Error: ...`), which sit far above the log's end, and for an NCCL collective timeout the watchdog's line plus the project frames of the stuck collective's Python stack. The runner itself only prints one status line per cell, plus a failed cell's last log lines; with `--background` that goes to `output/experiments/runner_<timestamp>.log`. With `--wandb`, every cell is **one** W&B run: the training run (its id is read back from `train/wandb/latest-run`), which the evaluation resumes to add the summary metrics (`cnw/<stat>`, `cnw/AP/<class>`, `framework/...(M)`, `latency/...`), eval args (`config.eval`) and a one-row table under `summary`: W&B merges same-key tables of all runs into one panel. EoMT's training run is in `--wandb-project` (default `atia-2026-experiments`), `group` = experiment, `name` = `<exp>-seed<N>`, `split_seed` in config; YOLO's is Ultralytics' own (project = the cell's output path with `/` → `-`, run `train`). If the training wasn't logged to W&B, the evaluation gets a new `job_type` eval run in `--wandb-project`. Ultralytics' own per-epoch training curves still include its box metrics. The YOLO batch-1 test pass takes ~6 min per cell, mostly Ultralytics' own per-image metric/mask bookkeeping (not counted in its speed); EoMT's `validate` takes ~4–11 min (see the table above).

```bash
uv run -m src.experiments --list
uv run -m src.experiments --background --wandb --device both  # everything, DDP on both GPUs; status in output/experiments/runner_<timestamp>.log, per-cell logs in output/experiments/<cell>/run.log
uv run -m src.experiments --experiments yolo-1024x592 --seeds 42 --device 0 epochs=1 fraction=0.02  # smoke run
uv run -m src.experiments --experiments eomt-1024x592 --seeds 42 --device 0 trainer.max_epochs=1 trainer.check_val_every_n_epoch=1 trainer.limit_train_batches=2 trainer.limit_val_batches=2  # EoMT smoke run (it must validate once to write best.ckpt)
```

The trailing overrides only reach training; the test evaluation always covers the whole split.
