# NDAK15013U — Advanced Topics in Image Analysis (ATIA)

**University of Copenhagen · Department of Computer Science · 2026**

Welcome to the ATIA project repository. This is the shared workspace for developing, documenting, and submitting course project code. **Each student has one project directory directly in the root of this repository, named after their GitHub username.**

Projects are organised by student, not by topic. You may work on CNNs and transformers, diffusion and other generative methods, foundation models for segmentation, or another topic agreed with your supervisor. Describe your topic and research question in your own `README.md`; you do not need to put your code in a predefined topic directory.

See the [official course description][course] for learning outcomes and assessment. Consult Absalon for project material, deadlines, collaboration rules, and submission requirements. **Submitting code here does not replace the individual written report.**

## Repository structure

The intended structure is:

```text
atia-2026/
├── README.md
├── LICENSE
├── template/                    # Generated example; do not develop your project here
├── your-github-username/         # Your project code and documentation
├── another-github-username/      # Another student's project
└── ...
```

These are **ordinary directories in one shared Git repository**, not independent repositories. Do not run `git init` inside your student directory or add a nested `.git` directory. Your code is versioned through the course repository. Git branches are working versions of that repository; the suggested research themes are not Git branches.

Keep changes inside your own directory. Do not modify another student's work or shared course files as part of a project submission. Use an identifier approved by the teaching team if your GitHub username conflicts with an existing shared directory. Never use confidential student or examination identifiers in public paths.

## Getting started

### 1. Clone the course repository and create a branch

You need Git, a GitHub account with permission to push a working branch, Python, and an appropriate project environment. The examples assume Bash or Zsh and a `main` default branch. On Windows, use Git Bash or adapt the commands to your shell. Contact the teaching team before starting if you do not have the required access; do not make a public fork of restricted course material.

```bash
git clone https://github.com/diku-dk/atia-2026.git
cd atia-2026

STUDENT_ID="your-github-username"
git switch main
git pull --ff-only
git switch -c "student/$STUDENT_ID"
```

Replace `your-github-username` with your actual username. Keep this terminal session open; subsequent commands reuse `STUDENT_ID`. When resuming work, set the variable again and switch to your existing branch with `git switch "student/$STUDENT_ID"`, without `-c`.

### 2. Generate your project with Cookiecutter

Install [Cookiecutter][cookiecutter] in the environment used for project generation:

```bash
python -m pip install cookiecutter
```

From the **root of the course repository**, run the [True Neutral Cookiecutter][upstream-template]:

```bash
cookiecutter gh:patrickmineault/true-neutral-cookiecutter
```

For example, answer its prompts as follows:

```text
project_name [project_name]: My ATIA project
repo_name [my_atia_project]: your-github-username
package_name [src]: atia_project
description [A truly neutral research cookie cutter]: A short description of my research question
```

Enter your actual username for `repo_name`, matching `STUDENT_ID`. Although the prompt says `repo_name`, it only determines the name of the generated directory: in this workflow, that directory remains part of the shared repository. Use a valid Python package name without spaces or hyphens for `package_name`. See the [template configuration][template-config].

**Do not use `template` as your project directory name, and do not overwrite an existing directory.** The shared `template/` is an example generated by the teaching team, not a reusable Cookiecutter input. Cookiecutter generation is a one-time setup step, not something to rerun over your ongoing project.

The generated structure is:

```text
your-github-username/
├── README.md
├── .gitignore
├── setup.py
├── atia_project/
│   └── __init__.py
├── data/
├── docs/
├── results/
├── scripts/
└── tests/
```

Add `configs/`, `notebooks/`, and other directories when useful. Keep reusable implementation code in your Python package, execution entry points in `scripts/`, and small results in `results/`. An existing project may retain an appropriate structure rather than using the template, provided it meets the documentation and submission requirements.

### 3. Protect data and local files

The upstream template does not automatically exclude datasets. Before adding data or making your first commit, append suitable rules to **your project's** `.gitignore`, for example:

```gitignore
# Keep the data documentation, not the datasets.
/data/*
!/data/README.md
/checkpoints/
/weights/
/logs/
/wandb/

# Python environments, build products, and caches.
.venv/
venv/
__pycache__/
*.py[cod]
*.egg-info/
.pytest_cache/
.ipynb_checkpoints/
build/
dist/

# Credentials and machine-specific files.
.env
.env.*
.DS_Store
```

Adapt these patterns to your project's storage locations. Do not commit full datasets, large checkpoints, personal or restricted images, passwords, API keys, tokens, or virtual environments. Keep data-access and preprocessing instructions in `data/README.md` and useful small result tables or figures in `results/`.

Ignore rules do not remove already tracked files. Inspect your staged changes and ask for help if sensitive files were committed. See [Git's ignore documentation][gitignore].

### 4. Create your project environment

Enter your generated directory before installing the project:

```bash
cd "$STUDENT_ID"
conda create --name "atia-2026-$STUDENT_ID" python=3.11 pip setuptools
conda activate "atia-2026-$STUDENT_ID"
python -m pip install -e .
```

The Python version is a starting point from the upstream template; adapt it to your dependencies. Install the packages required by your project and maintain an `environment.yml`, `requirements.txt`, or equivalent specification inside your own directory. Document how to recreate the environment and any GPU requirements. Avoid machine-specific paths in exported files. See the [Conda environment guide][conda-environments].

The template's message about syncing to GitHub is generic. **For this shared-folder workflow, do not create another Git repository or change the course repository's remote.** Return to the course root before running the commit commands below:

```bash
cd ..
```

## Working on your project

Commit meaningful changes regularly and push them to your student branch. From the course repository root:

```bash
git status
git add -- "$STUDENT_ID"
git diff --cached --stat
git diff --cached
```

Check that the staged changes contain only your intended work and no sensitive or large files. Then:

```bash
git commit -m "Update ATIA project for $STUDENT_ID"
git push -u origin HEAD
```

Stage only your directory rather than using `git add .` from the course root. To incorporate shared updates, first commit your changes, then run:

```bash
git fetch origin
git merge origin/main
```

Resolve any conflicts carefully, without deleting or overwriting another student's changes. See [Git's branching guide][git-branching].

## Project documentation

Your `README.md` should explain your research question, relevant papers, and the distinction between reused methods and your own implementation. Include setup instructions, dependency versions, dataset access and preprocessing, data splits, and exact commands to reproduce the relevant experiments.

Document experiment settings, random seeds, metrics, baselines, and how result tables or figures were generated. Summarise the main findings, approximate runtime or hardware needs, and known limitations. Keep reusable code separate from exploratory notebooks where practical, and add meaningful tests or sanity checks. These are reproducibility guidelines, not a replacement for project-specific assessment instructions.

## Submitting your code

The code-submission workflow is a pull request from your student branch into `main`; instructions on Absalon take precedence. Open a draft pull request for work in progress if helpful, and mark it ready for review by the announced deadline. Use a title such as `ATIA project — your-github-username — short project title`.

Include your project directory, research question, a summary of your changes, the commands you tested, any known limitations, and the full commit identifier of your submitted version. After pushing your final changes, obtain the identifier from your branch with:

```bash
git rev-parse HEAD
```

Verify that the pull request shows only intended changes and that your latest commit is visible on GitHub. Leave merging to the teaching team unless instructed otherwise. Later commits produce a different version; follow the course rules for changes after the deadline. See [GitHub's pull-request guide][pull-requests].

Submit the individual written report separately through the designated course system, identifying the same code version where requested.

## Course-hosted Cookiecutter template

For now, generate projects from the upstream template as described above. Once the teaching team has added and pushed a complete Cookiecutter input under `true-neutral-cookiecutter/`, the equivalent command, run from the course root, will be:

```bash
cookiecutter gh:diku-dk/atia-2026 --directory true-neutral-cookiecutter
```

For an available local copy, use:

```bash
cookiecutter ./true-neutral-cookiecutter
```

The selected template directory must contain `cookiecutter.json` and an unrendered project directory such as `{{cookiecutter.repo_name}}/`. Neither an empty directory nor the generated `template/` example is sufficient. Do not append a template subdirectory to the `gh:owner/repository` shorthand; select it with `--directory`. This option is supported in Cookiecutter 1.7 and later. See the [Cookiecutter directory documentation][cookiecutter-directory].

## Collaboration, privacy, and support

This is a shared repository: **separate directories and branches are not private workspaces**. People with read access can see committed work; a public repository is readable by anyone. Contact the teaching team before uploading work that requires restricted access. See [GitHub's repository documentation][repository-access].

Follow the course rules on collaboration, attribution, code reuse, and AI-assisted tools. Being able to see another student's code does not grant permission to copy it. Use issues for non-sensitive technical problems with the shared materials or template, and use the course communication channel for personal or assessment-related questions.
